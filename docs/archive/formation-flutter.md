Partie 1 : Fondations de la programmation
1 : Comprendre l’informatique et le numérique
Avant de plonger dans Dart et Flutter, il est essentiel de comprendre ce qu’est un ordinateur et comment il exécute un programme.
Un ordinateur est constitué de matériel (hardware) et de logiciels (software). Le processeur exécute des instructions, la mémoire stocke des données temporaires, le disque persiste les données à long terme. Les programmes sont écrits dans des langages de programmation et traduits en instructions que le processeur comprend.
Nous utiliserons Dart, un langage compilé en code machine ou en JavaScript selon la plateforme, pour écrire nos programmes.

Principaux concepts
Bit et octet : L’unité d’information la plus petite est le bit (0 ou 1). Un octet contient 8 bits.

Système binaire : les nombres sont représentés en base 2 (0 et 1).

Compilation vs interprétation : un compilateur traduit tout le code source en langage machine avant l’exécution, alors qu’un interpréteur exécute le code ligne par ligne. Dart combine ces stratégies (compilation JIT pour le développement avec hot reload, AOT pour la production).

Systèmes d’exploitation : Les OS (Windows, macOS, Linux, Android, iOS) gèrent les ressources et fournissent des API pour interagir avec le matériel.

2 : Algorithmes, variables et structures de contrôle
Un algorithme est une suite d’instructions permettant de résoudre un problème. Pour l’écrire, nous utiliserons du pseudo‑code ou un langage de programmation.
Dart est à typage fort : chaque variable a un type (int, double, String, bool, etc.). On peut déclarer une variable comme ceci :

int compteur = 0;
String message = "Bonjour!";
double prix = 9.99;
bool estValide = true;
Structures de contrôle
Séquences : exécution d’instructions dans l’ordre.

Conditionnelles (if/else, switch) : exécuter un bloc seulement si une condition est vraie.

Boucles (for, while, do/while) : répéter un bloc tant qu’une condition est vraie ou pour un nombre déterminé de tours.

for (int i = 0; i < 10; i++) {
print(i);
}

if (prix > 10) {
print("Prix élevé");
} else {
print("Prix correct");
}
Les structures de contrôle permettent de traduire la logique d’un algorithme en code.

3 : Fonctions et modularité
Les fonctions permettent de factoriser du code et de le réutiliser. Une fonction prend des paramètres, effectue un traitement et retourne un résultat.
En Dart, on définit une fonction ainsi :

int addition(int a, int b) {
return a + b;
}
On peut aussi utiliser des fonctions anonymes (lambdas) pour des opérations simples. Les fonctions sont des objets de première classe : elles peuvent être passées en paramètre et retournées par une autre fonction.

Portée et variables locales
Les variables déclarées à l’intérieur d’une fonction n’existent que pendant l’exécution de cette fonction. Les variables globales sont accessibles depuis n’importe quelle partie du code, mais leur utilisation doit être limitée pour éviter les effets de bord.

4 : Notions avancées : structures de données et complexité
Dans cette section, nous explorons des structures de données courantes et leur impact sur les performances.

Listes (tableaux) : structure linéaire indexée. Accès en O(1), insertion/suppression en fin en O(1) amorti.

Sets : collection d’éléments uniques. Basée sur un hash, l’ajout et la recherche s’effectuent en O(1).

Maps (dictionnaires) : associent des clés à des valeurs. Les opérations de recherche et d’insertion sont en O(1) en moyenne.

La complexité algorithmique permet d’estimer le temps d’exécution en fonction de la taille des données. Il existe différentes classes : O(1), O(n), O(log n), O(n^2), etc.
En Flutter, la performance est cruciale pour préserver une expérience fluide. Utiliser des structures de données appropriées et éviter les opérations coûteuses (comme les recherches inefficaces ou les listes non paginées) est indispensable
docs.flutter.dev
.

Partie 2 : Le langage Dart et la programmation orientée objet
5 : Découvrir Dart : syntaxe et types
Dart est un langage orienté objet développé par Google. Il est utilisé pour Flutter et peut être compilé en code natif ou JavaScript.

Caractéristiques principales
Typage statique avec inférence : Dart déduit le type si on utilise var, mais on peut également spécifier un type explicitement.

Null-safety : Introduite en Dart 2.12, cette fonctionnalité empêche les erreurs de type null en exigeant une déclaration explicite des types nullable (marqués par ?).

Collections puissantes : List, Set et Map avec un support complet des générateurs (for dans les littéraux) et de l’opérateur spread (...).

Fonctions de premier ordre et closures : les fonctions peuvent être passées comme arguments et retourner d’autres fonctions.

Syntaxe
Dart emprunte beaucoup de sa syntaxe à C et à Java : les blocs sont délimités par des accolades, les instructions terminées par un point‑virgule. Les opérateurs arithmétiques (+, -, *, /), logiques (&&, ||), de comparaison (==, !=, <, <=) et d’affectation (=, +=) sont familiers.

6 : Classes, objets, héritage et mixins
Dart est un langage orienté objet : tout est objet, même les nombres ou les fonctions. Une classe définit le plan d’un objet. Les instances sont créées à partir de la classe.

class Photo {
final String id;
final String title;
final DateTime date;

Photo({required this.id, required this.title, required this.date});
}
Constructeurs et paramètres nommés
Le constructeur s’écrit Photo({...}). Les paramètres required imposent leur présence. Dart propose aussi des constructeurs nommés (Photo.fromJson) pour fournir différentes manières de créer l’objet.

Héritage et interfaces
Les classes peuvent hériter d’une seule classe parente (extends) et implémenter plusieurs interfaces (implements). L’héritage permet de réutiliser du code, mais il est souvent préférable de privilégier la composition (avoir un attribut d’une autre classe) pour plus de flexibilité.

Mixins
Un mixin est une classe abstraite réutilisable. Il s’applique avec with pour ajouter des fonctionnalités à une classe sans créer de hiérarchie.
Par exemple, on peut créer un mixin LoggerMixin qui fournit une méthode log() à plusieurs classes.

7 : Génériques, exceptions et null-safety
Génériques
Les génériques permettent d’écrire du code réutilisable type-safe. Par exemple, List<int> est une liste de nombres entiers ; List<String> est une liste de chaînes. Les génériques s’utilisent aussi dans nos propres classes :

class Result<T> {
final T value;
final String? error;

Result.success(this.value) : error = null;
Result.error(this.error) : value = throw ArgumentError(error);
}
Exceptions
Dart gère les erreurs via des exceptions. On utilise try/catch pour capturer une erreur et throw pour en lancer une. Il est important de placer le code susceptible de produire une exception dans un bloc try et de gérer les erreurs pour éviter que l’application plante. Les exceptions non interceptées sont capturées par Flutter et envoyées à FlutterError.onError
docs.flutter.dev
.

Null-safety
La null-safety impose d’indiquer si une variable peut être nulle (String?) ou non (String). Ceci évite l’erreur classique “NullPointerException”. Pour accéder à une propriété d’un objet nullable, on utilise l’opérateur ?..
Exemple : int? length = name?.length;

11 : Comprendre Flutter et le widget tree
Flutter est un framework déclaratif : une interface est définie comme une hiérarchie de widgets immuables. Chaque widget décrit une partie de l’interface (un bouton, un texte, un conteneur). Le framework Flutter se charge de comparer l’ancienne et la nouvelle hiérarchie et de mettre à jour l’écran de manière efficace.

Les widgets se répartissent en deux grandes familles :

StatelessWidget : ils n’ont pas d’état interne et ne changent pas après leur création.

StatefulWidget : ils possèdent un état interne (classe State) qui peut changer ; lorsqu’on appelle setState(), Flutter reconstruit la partie affectée de l’interface.

Cycle de vie d’un StatefulWidget
La méthode createState() crée un objet State.

initState() est appelée une seule fois ; on y effectue les initialisations.

build(BuildContext context) est appelée à chaque fois que l’état change.

dispose() est appelée lorsque le widget est retiré de l’arbre.

Connaître ce cycle est essentiel pour gérer correctement la mémoire (écouteurs, contrôleurs).

15 : Layouts, contraintes et responsive design
La disposition des widgets est basée sur un système de contraintes. Flutter envoie des contraintes vers le bas de l’arbre (largeur et hauteur min/max), et chaque widget renvoie sa taille calculée vers le haut, puis le parent positionne l’enfant. Le guide des bonnes pratiques résume ce principe en disant que « les contraintes descendent, les tailles remontent et le parent définit la position »
docs.flutter.dev
.
Pour construire une interface adaptable :

Row et Column : alignent les enfants horizontalement ou verticalement.

Expanded et Flexible : demandent à un widget de prendre l’espace restant.

Container, Padding, Align, Center : gèrent la taille et l’alignement.

MediaQuery : donne des informations sur la taille de l’écran (utile pour adapter la mise en page).

LayoutBuilder : fournit les contraintes du parent et permet de changer la disposition selon la largeur disponible.

Responsive design
Pour adapter l’interface aux tablettes, aux grands écrans ou aux formats pliables, tu peux créer des dispositions différentes selon la largeur. Par exemple, afficher une grille en 3 colonnes sur téléphone, en 5 sur tablette. Les packages comme responsive_builder facilitent la gestion du responsive.

Partie 6 : Asynchronisme, I/O et accès aux fichiers
19 : Futures, async/await et gestion d’erreurs asynchrones
Dart fournit un modèle asynchrone basé sur les Futures et le event loop. Lorsqu’on exécute une opération longue (ex. lecture de fichier, requête réseau), Dart renvoie immédiatement un Future<T> qui sera complété ultérieurement avec un résultat ou une erreur. Les mots‑clés async/await simplifient l’écriture de code asynchrone.

Exemple :

Future<String> lireFichier(String chemin) async {
final file = File(chemin);
return await file.readAsString(); // attend la fin de la lecture
}

void main() async {
print('Début');
try {
final contenu = await lireFichier('data.txt');
print(contenu);
} catch (e) {
print('Erreur : $e');
}
print('Fin');
}
Sans await, la fonction renvoie immédiatement un Future<String>. En ajoutant await, Dart suspend l’exécution de la fonction courante jusqu’à ce que le futur soit complété. La documentation Dart explique que await permet à d’autres opérations de s’exécuter pendant l’attente
dart.dev
.

Gestion des erreurs
Pour gérer les exceptions dans les opérations asynchrones, enveloppe le code dans un bloc try/catch. Tu peux aussi utiliser on pour filtrer les types spécifiques d’erreurs.

20 : Streams et écoute d’événements continus
Un Stream représente une séquence asynchrone de données ou d’événements. Les streams sont utiles pour écouter des sources comme le clavier, la géolocalisation ou un flux réseau. Les Streams se consomment via une boucle await for ou avec stream.listen().
La documentation Dart explique que les streams fournissent des données une par une, qu’ils peuvent être à abonnement unique ou broadcast, et que l’on peut transformer un stream avec des méthodes comme map(), where() ou take()【968089704022735†L257-L276】.

Exemple :

Stream<int> generateNumbers() async* {
for (int i = 0; i < 5; i++) {
await Future.delayed(const Duration(milliseconds: 500));
yield i;
}
}

print('Nombre reçu : $n');
}
}

22 : Introduction à l’état : local vs partagé
La documentation Flutter distingue l’état éphémère (local) et l’état d’application (partagé ou persistant). L’état éphémère ne concerne qu’un widget et peut être géré via un StatefulWidget et setState()

23 : setState, Provider, Riverpod et Bloc
setState()
setState() est la méthode la plus simple pour mettre à jour l’état d’un widget. Lorsque l’on modifie une variable d’instance dans la classe State, on appelle setState(() {}); pour déclencher la reconstruction.

Provider
Provider encapsule l’utilisation d’InheritedWidget et ChangeNotifier. Un modèle (ChangeNotifier) émet des notifications lorsque l’état change, et les widgets qui consomment le modèle se reconstruisent. .

Riverpod

Bloc/Cubit
Bloc (Business Logic Component) applique le pattern d’architecture qui sépare les événements (Inputs) des états (Outputs). Les blocs reçoivent des événements et émettent des états via un Stream. Les Cubit sont une version simplifiée où chaque méthode change directement l’état. Bloc est adapté aux applications complexes avec de nombreux états.

24 : Séparation des couches et architecture MVVM
Pour maintenir et faire évoluer une application, Flutter recommande de séparer l’interface (UI) de la logique métier. La documentation Flutter sur l’architecture préconise de diviser une app en deux couches : l’UI et la couche de données
docs.flutter.dev
.
L’architecture MVVM (Model‑View‑ViewModel) propose les rôles suivants :

View : widgets qui affichent les données et gèrent les interactions utilisateur. Ils ne contiennent pas de logique métier.

ViewModel : classe qui récupère les données depuis les dépôts, les transforme en états prêts à être affichés, maintient l’état de l’UI et expose des méthodes (actions) au View
docs.flutter.dev
.

Repository : composant de la couche de données qui fournit une API simple pour accéder aux données. Il interagit avec des services (bases, API) et représente le single source of truth
docs.flutter.dev
.

Service : classe qui encapsule un accès technique (PhotoService, ApiService).

UseCase/Domain (facultatif) : couche logique qui contiendra la logique métier complexe, les règles et les validations
docs.flutter.dev
.

Cette séparation favorise la testabilité et la réutilisabilité. Les vues sont légères, les ViewModels orchestrent les appels et gèrent l’état, les dépôts isolent les sources de données et les services communiquent avec l’extérieur.

34 : Animations implicites et explicites
Les animations implicites permettent d’animer automatiquement la transition entre deux valeurs sans gérer un AnimationController. Des widgets comme AnimatedContainer, AnimatedOpacity ou TweenAnimationBuilder prennent un paramètre duration et animent le changement

class FadeIn extends StatefulWidget {

State<FadeIn> createState() => _FadeInState();

late final AnimationController _controller;
late final Animation<double> _animation;

@override
void initState() {
super.initState();
_controller = AnimationController(duration: const Duration(seconds: 1), vsync: this)..forward();
_animation = CurvedAnimation(parent: _controller, curve: Curves.easeIn);
}

@override
void dispose() {
_controller.dispose();
super.dispose();
}

@override
Widget build(BuildContext context) {
return FadeTransition(
opacity: _animation,
child: const Text('Hello'),
);
}
}

38 : Appels de méthodes plateforme via MethodChannel
Pour interagir avec les API natives sans créer un plugin séparé, utilise MethodChannel. Un channel est identifié par une chaîne unique (ex. samples.flutter.dev/battery) et sert à envoyer des messages entre Dart et la plateforme.

Côté Flutter :

static const MethodChannel _channel = MethodChannel('samples.flutter.dev/battery');

Future<int> getBatteryLevel() async {
try {
final int level = await _channel.invokeMethod<int>('getBatteryLevel')!;
return level;
} on PlatformException catch (e) {
throw 'Erreur : ${e.message}';
}
}
Côté Android (Kotlin) :

MethodChannel(flutterEngine.dartExecutor.binaryMessenger, "samples.flutter.dev/battery")
.setMethodCallHandler { call, result ->
if (call.method == "getBatteryLevel") {
val batteryLevel = getBatteryLevel()
if (batteryLevel != -1) {
result.success(batteryLevel)
} else {
result.error("UNAVAILABLE", "Battery level not available.", null)
}
} else {
result.notImplemented()
}
}
La documentation explique que le nom du canal doit être unique et que les méthodes renvoient un résultat ou une erreur
docs.flutter.dev
.

Partie 12 : Caching, offline-first et synchronisation
40 : Caching : mémoire vs persistance
Le caching permet de stocker temporairement des données pour éviter de refaire un calcul ou un chargement coûteux.
Deux types de cache :

Cache en mémoire : rapide et volatile. Utile pour des sessions courtes (ex. miniatures d’images). Un cache en mémoire se réinitialise lorsque l’app est fermée.

Cache persistant : sauvegarde sur disque (SharedPreferences, fichier, base de données). Utile pour conserver l’état entre les sessions.

Le guide Flutter sur le caching recommande d’implémenter un repository qui stocke en mémoire et sur disque. Il préconise d’injecter les dépendances (service distant, base locale) et d’éviter d’hardcoder les clés de caching
docs.flutter.dev
. Une solution hybride consiste à utiliser shared_preferences pour les petites valeurs et une base locale (SQLite/Isar) pour les collections importantes
docs.flutter.dev
.

41 : Application offline-first
Une application offline-first continue de fonctionner lorsque le réseau est coupé. Le guide Flutter explique qu’une telle app combine des sources de données locales et distantes : un repository utilise une base locale comme source de vérité et synchronise avec un service distant lorsque la connectivité est disponible
docs.flutter.dev
. Le repository fournit un flux (Stream) de données pour notifier la vue des mises à jour
docs.flutter.dev
.

Étapes pour un pattern offline-first :

Stocker la donnée dans une base locale (SQLite/Isar).

Lors d’une requête, lire d’abord la base locale, puis, si le réseau est disponible, faire un appel API et mettre à jour la base.

Exposer un stream d’objets (ex. Stream<List<Photo>>) pour que les vues se mettent à jour automatiquement.

Gérer les conflits (ex. lorsque la suppression d’une photo échoue côté serveur).

42 : Conception d’un Repository caché et flux de synchronisation
Pour généraliser l’approche offline-first, crée une interface BaseRepository<T> avec les méthodes suivantes :

abstract class BaseRepository<T> {
Future<void> save(T item);
Stream<List<T>> watchAll();
Future<List<T>> refresh(); // force un appel au serveur
}

Lorsqu’une nouvelle page est chargée, le repository ajoute les éléments et notifie les listeners. En background, le repository synchronise régulièrement (ex. toutes les 5 minutes) avec un serveur fictif.

60 : Architecture Clean et Domain-driven design
Au-delà de MVVM, certaines applications nécessitent une architecture encore plus modulaire. Clean Architecture sépare l’application en trois couches concentriques :

Domain : contient les entités, les use cases et les interfaces des dépôts. Le domaine ne dépend d’aucune implémentation concrète.

Data : implémente les interfaces du domaine (repositories) et communique avec les sources (services, bases).

Presentation : équivalent de l’UI ; dépend du domaine (via les use cases) mais pas de la couche data.

Domain-Driven Design (DDD) approfondit la modélisation du domaine : on identifie des agrégats, des entités et des services, et l’on définit des value objects. Les couches communiquent via des ports et adaptateurs.
L’avantage de Clean Architecture est la testabilité (les dépendances sont inversées), la flexibilité (on peut changer la base ou le framework UI) et la cohérence du domaine.
